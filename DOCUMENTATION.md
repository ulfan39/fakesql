# FakeSQL - a "Faker" written in SQL

FakeSQL generates realistic fake user contact data **entirely inside PostgreSQL**:
full name, address, geolocation, physical attributes, phone number and e-mail.
It is a small library of stored routines in the schema `fk`; the web application
(Python/FastAPI) only calls `fk.generate_users(...)` and renders the result.

* Supported locales out of the box: **English (USA)** `en_US`, **German (Germany)** `de_DE`.
  Adding a locale needs data only, no code (see [Adding a locale](#adding-a-locale)).
* **Deterministic**: the same `(locale, seed, batch, index)` always gives the same user.
* **Fast and set-based**: no global state, no sequences, no random() calls. About 4,000 users/second per connection (see [Benchmark](#benchmark)).

---

## 1. Quick start

```sql
-- 10 users, locale de_DE, seed 42, batch 0
SELECT * FROM fk.generate_users('de_DE', 42, 0, 10);

-- the next batch for the same arguments
SELECT * FROM fk.generate_users('de_DE', 42, 1, 10);

-- exactly one user (same values as the corresponding row of the batch)
SELECT * FROM fk.generate_user('en_US', 7, 3, 4);

-- speed test
SELECT * FROM fk.benchmark('en_US', 1, 20000);
```

Result columns of `fk.generate_users`:

| column | type | description |
|---|---|---|
| `seq` | bigint | position of the user: `batch * batch_size + idx + 1` |
| `full_name` | text | name with locale-specific variations (title, middle name, ...) |
| `gender` | char(1) | `M` / `F` |
| `address` | text | street, house number, optional unit, city, postcode, formatted per locale |
| `latitude`, `longitude` | double | degrees, **uniformly distributed on the sphere** |
| `height_cm`, `weight_kg` | integer | whole cm / kg, normally distributed, correlated (rho = 0.5) |
| `eye_color` | text | discrete, weighted per locale |
| `phone` | text | several formats per locale |
| `email` | text | built from the transliterated name, several patterns and domains |

### Installation

```bash
# psql
for f in db/0*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f $f; done
# or, without psql (Windows friendly)
pip install "psycopg[binary]"

```

## 2. Design

### 2.1 Reproducibility without state

There is no stored generator state. Every "random" number is a **pure function of a text key**:

```
key = locale | seed | batch | index-in-batch | salt
```

`salt` is a short name of the attribute (`'first'`, `'city'`, `'height'`, ...), so every attribute of every user
gets its own independent number. Consequences:

* the same arguments always give the same data (md5 is stable across PostgreSQL versions and platforms);
* user *n* does not depend on users *n-1*, so batches can be computed in any order, in parallel, or one user at a time;
* the batch size does not influence the content: user `(batch 3, idx 7)` is identical whether the page shows 10 or 100 users per batch.

### 2.2 Data model (extensibility)

All locales share the same tables; a `locale` column distinguishes them.

| table | content |
|---|---|
| `fk.locales` | one row per locale: `code`, UI `title`, `postcode_pattern`, `house_number_max` |
| `fk.names` | **all** first and last names of all locales (`kind` = first/last, `gender`, `weight`) |
| `fk.lexicon` | every other word list or pattern list: `kind` + `sub` + `value` + `extra` + `weight` |
| `fk.translit` | locale-specific replacements for e-mail addresses (`ü` -> `ue`) |
| `fk.body_stats` | mean and standard deviation of height and weight per locale and gender |
| `fk.pools` | pre-computed weighted pools (arrays), generated by `CALL fk.refresh_pools()` |

`fk.lexicon.kind` values: `title` (sub = gender), `name_pattern`, `street_base`, `street_type`, `city`
(extra = region), `address_pattern`, `phone_pattern`, `email_pattern`, `email_domain`, `eye_color`.

Current size (en_US + de_DE): about 4,100 names (2,700 first names, 1,400 last names), 1,700 street words,
24 street types, 690 cities, plus patterns. This gives several hundred thousand distinct name combinations per locale
and, together with addresses, phones and e-mails, no practical repetition for 100,000 - 1,000,000 users.
(Measured: 100,000 users en_US -> 89,468 distinct names, 93,487 distinct e-mails, 100,000 distinct addresses.)

Format patterns are data, not code. Tokens in `{braces}` are replaced by generated parts; in phone masks
`#` is any digit and `N` a digit 2-9:

| pattern kind | example (en_US) | example (de_DE) |
|---|---|---|
| name | `{title} {first} {middle} {last}` | `{first} {last}-{last2}` |
| address | `{num} {street}, Apt {unit}, {city}, {region} {zip}` | `{street} {num}, {floor}. OG, {zip} {city}` |
| phone | `(N##) N##-####` | `+49 17# #######` |
| e-mail | `{f}.{last}` | `{last}.{first}` |

Weights control how often each pattern or value appears (they are relative, they need not sum to 100).

## 3. Routine reference

All routines live in schema `fk`. `p_prefix` is the per-user key prefix returned by `fk.key_prefix`.

### 3.1 Random number generation (`db/02_random.sql`)

| routine | arguments | returns | algorithm |
|---|---|---|---|
| `key_prefix(p_locale, p_seed, p_batch, p_idx)` | text, bigint, int, int | text | `locale\|seed\|batch\|idx\|` - computed once per user |
| `u(p_prefix, p_salt)` | text, text | double in [0,1) | first 52 bits of `md5(prefix \|\| salt)` divided by 2^52 (52 bits fit exactly into a double mantissa) |
| `rand_uniform(p_prefix, p_salt, lo, hi)` | | double in [lo,hi) | `lo + (hi-lo)*u` |
| `rand_int(p_prefix, p_salt, lo, hi)` | | integer in [lo,hi] | `lo + floor(u*(hi-lo+1))` |
| `rand_normal(p_prefix, p_salt, mean, sd)` | | double | **Box-Muller**: `mean + sd * sqrt(-2 ln(1-u1)) * cos(2 pi u2)`, with two independent uniforms `u1`, `u2` (salts `#n1`, `#n2`) |
| `rand_sphere(p_prefix, p_salt)` | | (latitude, longitude) | see 4.2 |
| `rand_digits(p_prefix, p_salt, n)` | | text | n decimal digits from the low 13 decimal digits of a 52-bit hash (bias < 0.1 %), chained for n > 13 |

### 3.2 Lookup and text helpers (`db/03_text.sql`)

| routine | description |
|---|---|
| `CALL refresh_pools()` | rebuilds `fk.pools` from `fk.names` and `fk.lexicon`: arrays `vals`, `extras`, `cum` (cumulative probability). **Must be called after changing the data.** |
| `get_pool(locale, kind, sub)` | loads one pool (primary-key lookup); raises a clear error if it does not exist |
| `pick_idx(cum[], u)` | weighted pick by **inverse transform sampling**: binary search for the first `cum[i] > u`, O(log n) |
| `render(pattern, keys[], vals[])` | replaces `{key}` placeholders |
| `fill_pattern(pattern, prefix, salt)` | fills digit masks (`#` 0-9, `N` 2-9) |
| `slugify(text, src[], dst[])` | lower-case ASCII for e-mail: locale replacements first (`ä`->`ae`), then the standard PostgreSQL `unaccent` extension strips the remaining accents (`ř`->`r`, `ł`->`l`), everything else is removed |

### 3.3 Attribute generators and public API (`db/04_generate.sql`)

| routine | arguments | description |
|---|---|---|
| `gen_gender(prefix)` | | `M` or `F`, 50/50 |
| `gen_street(base, type, type_extra)` | | `Oak` + `Street` -> `Oak Street`; German types are *glued*: `Linden` + `straße` -> `Lindenstraße` |
| `gen_phone(prefix, pattern)` | | digit mask filled with hash digits |
| `gen_email(prefix, pattern, domain, first, last, src[], dst[])` | | local part from a weighted pattern (`{first} {last} {f} {l} {nn} {yy}`) + domain; names are transliterated |
| `gen_body(prefix, h_mean, h_sd, w_mean, w_sd)` | | height and weight, see 4.3 |
| `generate_range(locale, seed, batch, first_idx, count, batch_size)` | | core generator: loads the pools once, then builds each user from its own key prefix; returns `SETOF fk.fake_user` |
| **`generate_users(locale, seed, batch, size = 10)`** | text, bigint, int, int | **public API**: one batch |
| `generate_user(locale, seed, batch, idx, batch_size = 10)` | | one user at an exact position |
| `benchmark(locale, seed, total, batch_size = 1000)` | | returns `(users, seconds, users_per_second)` |

#### How a user is assembled

1. **gender** - fair coin from `u(prefix,'gender')`.
2. **name** - a weighted `name_pattern` decides the variation (plain, with title, with middle name or initial, double surname, "Last, First", ...).
   Only the parts that the pattern needs are drawn. First names depend on the gender, last names are weighted by real frequency where
   the source data had it (en_US), titles depend on gender and locale (`Mr.`/`Ms.`/`Mrs.`/`Dr.`, `Herr`/`Frau`/`Prof. Dr.`).
3. **address** - weighted `address_pattern`; street = weighted base word + weighted type; the house number is
   `1 + floor(u^3 * max)` which skews towards small numbers (many "12", few "4711"); optional apartment/floor; city (with region
   for the US); postcode from the locale mask.
4. **geolocation** - `rand_sphere`.
5. **height, weight** - `gen_body`.
6. **eye colour** - weighted discrete choice per locale.
7. **phone** - weighted format mask per locale.
8. **e-mail** - weighted pattern, domain weighted per locale.

## 4. Algorithms in detail

### 4.1 Uniform numbers

`md5()` of the key is a well-mixed 128-bit value. Taking 52 bits gives an integer in [0, 2^52); dividing by 2^52 yields a
double that is uniform on [0,1) and never equals 1 (so `ln(1-u)` and weighted picks are always safe).
Chi-square tests on 200,000 draws per seed give statistics in the expected range (see Validation).

### 4.2 Points uniformly distributed on a sphere

Drawing latitude uniformly from [-90, 90] and longitude from [-180, 180] is **wrong**: the area of a latitude band
is proportional to `cos(lat)`, so points would crowd near the poles (33 % of them would lie above 60 degrees, but only 13.4 % of the sphere's
surface does). The correct construction (Archimedes' hat-box theorem): the height `z = sin(lat)` of a uniform point on the sphere
is uniform on [-1, 1]. Therefore

```
longitude = 360 * u1 - 180
latitude  = degrees( asin( 2 * u2 - 1 ) )
```

with independent uniform `u1`, `u2`. The density of latitude then is proportional to `cos(lat)` as required.

### 4.3 Normal distribution, height and weight

`rand_normal` uses the Box-Muller transform: for independent uniforms `u1, u2`, the number
`z = sqrt(-2 ln u1) * cos(2 pi u2)` is standard normal; `mean + sd*z` is `N(mean, sd^2)`.

Height and weight of real people are positively correlated, so `gen_body` draws

```
zh = N(0,1)            height  = h_mean + h_sd * zh
z2 = N(0,1)            weight  = w_mean + w_sd * (rho*zh + sqrt(1-rho^2)*z2)      rho = 0.5
```

`rho*zh + sqrt(1-rho^2)*z2` is again exactly `N(0,1)`, so both marginals stay normal and corr(height, weight) = 0.5.
Values are cut at +-4 sigma and rounded to **whole centimetres and kilograms** (a finer resolution would be meaningless: a person's height already changes by about 1 cm during a day). Means and standard deviations come from `fk.body_stats` per locale and gender
(e.g. de_DE men: 180.3 cm / 7.2, 85.0 kg / 12.5).

### 4.4 Weighted choice (names, cities, patterns, eye colours)

`refresh_pools()` stores for every list the cumulative distribution `cum[i] = (w1+...+wi)/(w1+...+wn)` as an array.
A draw `u` selects the first `i` with `cum[i] > u` (binary search). A value with weight `w` is therefore chosen with probability `w / sum(w)`.
Pools are loaded once per `generate_users` call, so the per-user cost does not involve any table access.

### 4.5 Names, e-mail and locale specific details

* Name variations come from patterns; examples: `Dr. Anna Maria Schmidt`, `Mr. David Antonio Juarez`, `Hellwig, Irmhild`, `Maximilian Weber-Koch`.
* E-mail local parts are built from the transliterated name: `Jähn` -> `jaehn`, `Gómez` -> `gomez`, `Dvořák` -> `dvorak`, so addresses are valid ASCII. The `unaccent` extension is installed by `db/01_schema.sql` (`CREATE EXTENSION IF NOT EXISTS unaccent`).
* German street types are glued to the base word (`Goethe`+`straße`), English types are separate words.

## 5. Adding a locale

1. Insert a row into `fk.locales` (`code`, `title`, `postcode_pattern`, `house_number_max`).
2. Insert first names (`kind='first'`, gender `M`/`F`) and last names (`kind='last'`, gender `U`) into `fk.names`.
3. Insert into `fk.lexicon` for the new locale: `title` (sub `M` and `F`), `name_pattern`, `street_base`, `street_type`
   (`extra='glued'` if the type is attached to the word), `city`, `address_pattern`, `phone_pattern`, `email_pattern`,
   `email_domain`, `eye_color`.
4. Insert two rows into `fk.body_stats` (`M`, `F`) and, if needed, rows into `fk.translit`.
5. `CALL fk.refresh_pools();`

Example (the data of the two shipped locales is loaded exactly like this by `db/05_seed_data.sql`, generated by `tools/build_seed.py`):

```sql
INSERT INTO fk.locales VALUES ('xx_XX', 'Example', '#####', 200);
INSERT INTO fk.names (locale, kind, gender, value, weight) VALUES ('xx_XX','first','M','Max',3), ('xx_XX','first','F','Eva',3), ('xx_XX','last','U','Muster',1);
-- ... lexicon rows, body_stats rows ...
CALL fk.refresh_pools();
SELECT * FROM fk.generate_users('xx_XX', 1, 0, 5);
```

No routine has to be changed.

## 6. Validation

`tools/validate.sql` generates 100,000 en_US users and checks the distributions
(result of one run):

| check | result | expectation |
|---|---|---|
| chi-square of sin(latitude) in 10 bins | 4.57 | < 16.92 (9 dof, 5 %) |
| chi-square of longitude in 12 bins | 11.05 | < 19.68 (11 dof, 5 %) |
| share of points with abs(latitude) > 60 deg | 13.26 % | 13.40 % for a uniform sphere (naive method: 33.33 %) |
| height men: mean / sd | 175.4 / 7.60 | 175.3 / 7.6 |
| height women: mean / sd | 161.5 / 7.11 | 161.5 / 7.1 |
| weight men / women: mean / sd | 89.7 / 15.05, 77.0 / 15.06 | 89.7 / 15, 77.0 / 15 |
| corr(height, weight) | 0.50 | 0.50 |
| eye colours brown/blue/hazel/green/gray | 45.1 / 27.0 / 18.0 / 8.9 / 1.0 % | 45 / 27 / 18 / 9 / 1 % |
| same arguments -> same data | true | true |
| other seed -> other data | true | true |
| one user equals its row inside the batch | true | true |
| distinct addresses in 100,000 users | 100,000 | - |

## 7. Benchmark

`SELECT * FROM fk.benchmark(locale, seed, users, batch_size)` generates the users inside the database and measures wall-clock time
(single connection, no network, results aggregated by `count(*)`). `python tools/benchmark.py` runs it for all locales
(best of three runs of 20,000 users). The web app has a **Benchmark** link that runs the same function against the deployed database.

Run on the development machine (PostgreSQL 16.15, 2 vCPU container):

| locale | batch size | users | seconds | users/second |
|---|---|---|---|---|
| de_DE | 10 | 20000 | 5.251 | 3,809 |
| de_DE | 1000 | 20000 | 4.980 | 4,016 |
| en_US | 10 | 20000 | 4.969 | 4,025 |
| en_US | 1000 | 20000 | 4.665 | 4,287 |

**What costs time:** about 25 hash computations per user, around a dozen weighted picks and the string assembly in PL/pgSQL
(roughly 230-250 microseconds per user). Pools are cached in arrays so there is no table access per pick.
The routines are marked `PARALLEL SAFE`, so independent batches can be spread over several workers or connections.
